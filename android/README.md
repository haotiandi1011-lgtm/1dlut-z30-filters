# Z30 写入端（Android）

把一条影调曲线写进尼康 Z30 的自定义影调槽位 C1–C9，写完立刻读回逐字节校验。

曲线的来源有三种，都是本机完成、不需要联网：

1. **内置预设**——121 套随 APK 打包，选中即用
2. **导入配方**——电脑上导出的 `.z30` 配方包
3. **本机拟合**——直接选一张照片，手机上算出 256 点曲线（0.2.0 起）

> **实测环境**：iQOO Neo9 + 尼康 Z30，C-to-C 线直连。写入 C9 → 读回逐字节一致 → 相机成像正常、参数可调。

## 为什么预设是「预生成载荷」

内置预设的曲线、控制点、名称、参数在**桌面端生成时**就已经封成 614 字节载荷
（`tools/gen_android_presets.py` → `assets/builtin_presets.json`），手机端只负责搬运。
这样「手机上选的」和「电脑上写的」是同一段字节，不存在两边算法略有差别的问题。

`tests/run_tests.py` 里有一条守卫：拿安卓资源里的每条载荷去和桌面端曲线逐点比对，
**改了预设忘了重新生成资源会直接失败**。

## 本机拟合（照片 → 曲线）

选一张照片，手机上直接做**影调分布迁移**：把「典型场景」的亮度分布映射到参考图的
亮度分布上，得到一条单调的 256 点曲线，落成 `.z30` 配方进本机配方库并自动选中，
写入走的是和导入配方完全相同的链路（备份 → 写 → 逐字节校验）。

- **支持 JPG / PNG / HEIC**（HEIC 需要 Android 9 以上；RAW 如 NEF / CR2 系统解不了，不支持）
- **算法与电脑端同一条**：`tools/gen_android_fit_data.py` 用桌面端代码生成金标准，
  JVM 单测逐点比对（256 点差 ≤ 2 个 15 位码值）；再用真实照片复核，双端曲线逐点一致
- **指标口径**：只报「影调贴合误差（灰阶）」，单位是 8 位码值。单张照片没有真值，
  **不给 ΔE、不给还原度百分比**——参考图的色彩个性（色偏、饱和度、分色相）1D 曲线
  本来就表达不了，这一点和电脑端同图模式一致
- **告警含义**：参考图大片贴黑/贴白（换一张层次更完整的）、贴合偏差偏大（换一张影调
  更连贯的）、色彩很浓（提醒影调能贴近但色彩个性进不了机身）

## 为什么只有一条曲线

机身载荷里只有一条作用到 R/G/B 的 256 点曲线（512 字节），没有 3D LUT、没有色彩矩阵。
所以手机上无论走哪条来源，最终产出的都是「一条曲线 + 几个参数」，不存在「手机上能做 3D」这种可能。

## 能做什么

| 能力 | 说明 |
|---|---|
| 内置预设 | 121 套随 APK 打包，挑一条即落成配方，不用电脑、不用联网；不需要的可以隐藏，随时恢复 |
| 照片拟合 | 选一张照片直接算曲线，落成配方并自动选中；只迁移影调，见上节口径 |
| 配方回收站 | 删掉的配方进回收站（应用私有目录），能单条/全部恢复，也能彻底删除；支持多选批量删 |
| 照片对比 | 用你自己的照片套当前曲线，拖动分割线对比；满意就「保存」——先选格式（PNG 无损 / JPG 高质量），按原始分辨率导出（走系统另存为对话框选位置） |
| 本机备份 | 每次写入前自动备份原槽位；可从备份恢复（仅 614 字节），也可以删除不要的备份（两段式确认） |
| 导入配方 | `.z30` 配方包；也接受裸的 614 字节载荷 `.bin` |
| 读槽位 | 连接后一次读出 C1–C9 的名称与形态（完整配方 / 仅参数 / 空） |
| 写入槽位 | 默认 C9，可改；写前自动把原内容备份到手机 |
| 改名称 | ≤19 字符 ASCII（机身字段限制，中文会被替换成 `?`） |
| 改参数 | 锐化 / 清晰度 / 饱和度，跟着曲线一起进机身 |
| 读回校验 | 写完立刻读回，逐字节比对，不一致直接报错 |
| 恢复 | 从本机备份把某个槽位写回去（仅 614 字节备份可恢复） |

**不做**：整体色偏、分色相调整、分离色调、去饱和以外的色彩操作、删除槽位（`0x90CE` 是破坏性的，本应用不实现）。

## 构建

### 方案一：GitHub Actions（推荐，不用装 Android SDK）

推到 `main` 自动构建，或在 Actions 页面手动 `Run workflow`。
产物在本次运行的 **Artifacts → `z30tone-writer-apk`**，下载解压即可安装。

需要发布签名时，在仓库 Secrets 里配这四项，工作流会额外产出签名的 release 包：

| Secret | 内容 |
|---|---|
| `Z30_KEYSTORE_BASE64` | keystore 文件的 base64（`base64 -w0 z30.jks`） |
| `Z30_STORE_PASSWORD` | keystore 口令 |
| `Z30_KEY_ALIAS` | 密钥别名 |
| `Z30_KEY_PASSWORD` | 密钥口令 |

打 tag（`v0.1.0`）时会自动把 APK 挂到对应的 GitHub Release。

### 方案二：本地构建

要求：JDK 17、Android SDK Platform 35、Build-Tools 35。

```bash
cd android
echo "sdk.dir=/path/to/Android/Sdk" > local.properties   # Windows 用 D:/tools/android-sdk 这种正斜杠写法
./gradlew :app:assembleDebug          # Windows 命令行用 gradlew.bat :app:assembleDebug
# 产物：app/build/outputs/apk/debug/app-debug.apk
```

首次在 Linux/macOS 上运行如果提示 permission denied，先 `chmod +x gradlew`。
用 Android Studio 直接打开 `android/` 目录也可以。

### 单元测试

```bash
cd android
./gradlew :app:testDebugUnitTest      # Windows：gradlew.bat :app:testDebugUnitTest
```

覆盖 614 字节载荷的构建/解析、参数编码（真机回读的样本值）、名称 ASCII 规则、大端 LUT、
`.z30` 包的边界情况，以及拟合三件套：

- `ToneCurveTest`——单调、端点不漂、量化不塌陷（塌陷告警带**材料性阈值**：只有丢掉
  4 个以上 8 位码值的平段才算缺陷，肩部那种 1–3 个码值的平滑压肩不报）
- `ColorimetryTest`——Lab / CIEDE2000 与电脑端逐项对齐
- `FitParityTest`——金标准逐点比对（256 点差 ≤ 2 个 15 位码值）、黑位守卫、
  **口径守卫**（单图拟合的产物里不许出现会被读成 ΔE 的键）

这些都在 JVM 上跑，不需要相机。

> **Windows 中文路径的已知限制**：如果仓库放在 `D:/GitHub逆向z30滤镜` 这类含中文的目录，Gradle 的测试工作进程会加载不到测试类，
> 报 `ClassNotFoundException: ...Test`（Java 在 Windows 上解类路径的编码问题，与本项目代码无关）。
> APK 编译不受影响；要本地跑测试，把仓库放到纯英文路径即可，或者直接看 GitHub Actions 里的测试结果。

### 出包后的验收

```bash
python tools/check_android_apk.py     # 默认查 android 的 debug 包，也可传 APK 路径
```

确认 dex 里能搜到 `PhotoFit / FitUi`（拟合在包里）、`assets/builtin_presets.json`
仍是 121 套。CI 的产物名里带版本号，注意和工作流的 `Collect APKs` 步骤一起改。

## 使用步骤

1. 相机开机，`USB 模式` 设为 **MTP/PTP**，用数据线接到手机（需要手机支持 USB OTG）
2. 应用会自动拉起；没拉起就点「连接相机」，在系统弹窗里允许访问
3. 选一条曲线：内置预设里挑、从电脑导入 `.z30`，或直接「从照片生成曲线」
4. 选目标槽位（**第一次建议 C9**）
5. 点「写入」→ 确认 → 看结果

写入结果的三种情况：

- **读回一致**：机身已经拿到这份曲线，切到对应 C 槽位即可拍摄
- **有 N 字节不一致**：相机没接受完整数据，界面会列出偏移；原内容可从备份恢复
- **报错**：看界面下方的运行日志，常见原因是相机休眠、USB 被系统占用、线材只供电不传数据

## 相机侧的三个坑

1. **名称只认 ASCII**，最长 19 字符。中文会被替换成 `?`，这是机身限制。
2. **曲线之后还有白平衡增益**（`out = WB_gain × f(in)`）。同一份配方在不同白平衡下效果不同，严肃复现要固定白平衡。
3. **对比度/亮度写不进去**。有自定义曲线时这两个参数被机身禁用，写了也不生效，所以界面里没有它们。

## 写入报错怎么排（一加 / ColorOS 机型看第 4 条）

1. **错误码 -1（写入失败）**：多数是相机刚休眠（半按快门唤醒）、正在回放或翻菜单、
   或线材只供电不传数据。失败后应用会清理 USB 端点并自动重新握手（日志里能看到），
   **直接再点一次「写入」**即可；相机断开了就拔插后点「连接相机」。
2. **读相机超时**：相机休眠、不在 MTP/PTP 模式，或 USB 供电不足。
3. **USB 接口被系统占用**：拔插相机重连一次通常就好。
4. **一加 / realme / OPPO（ColorOS）专项**：
   - 设置里的「**OTG 连接**」要开启，并**关掉「OTG 自动关闭」**（10 分钟无操作会被系统掐断）；
   - 电池/省电设置里**不要限制本应用**（允许后台运行）；
   - 别经扩展坞/Hub，直连最稳。

## 安全约定

- 只写 614 字节的完整配方，不碰固件、不刷机
- 写前备份原槽位到手机私有目录，写后立刻读回校验
- 不做「自动重试」「自动清理」这类用户看不见的动作
- `0x90CE` 删槽不实现：它会把配方直接删掉，桌面端已有前人踩坑记录

## 代码地图

| 文件 | 职责 |
|---|---|
| `core/Payload.kt` | 614 字节载荷的解析/构建、参数编码、逐字节比对 |
| `core/Recipe.kt` | `.z30` 配方包读写 |
| `core/Slots.kt` | 槽位常量与显示名 |
| `core/Preview.kt` | 照片对比：解码、缩放、256 点查表 |
| `core/fit/PhotoFit.kt` | 单图拟合主流程：分位数匹配 → 单调样条 → 量化 → 判据 |
| `core/fit/ToneCurve.kt` | 单调三次样条（PCHIP）、保序回归、量化与塌陷检测 |
| `core/fit/Colorimetry.kt` | Lab / CIEDE2000 / 分位数（与电脑端逐项对齐） |
| `core/fit/PhotoLoader.kt` | 照片 → 排序亮度数组（JPG / PNG / HEIC，12MP 上限） |
| `core/fit/CanonicalPool.kt` | 「典型场景」513 个分位点（由桌面端导出，勿手改） |
| `usb/UsbPtp.kt` | PTP over USB：握手、`0x90CC` 读、`0x90CD` 写 |
| `usb/CameraController.kt` | 备份 → 写 → 读回校验 |
| `usb/UsbHub.kt` | USB 权限与热插拔 |
| `data/Stores.kt` | 配方与备份的本地存储（含回收站） |
| `data/BuiltinPresets.kt` | 读 `assets/builtin_presets.json`，内置预设（614 载荷 + 名称/分类） |
| `ui/` | Compose 界面与状态机 |
